# Issue #50: personal weight goals

The dashboard now reads a separate `WeightGoal` model instead of the shared 77 kg
constant. A Cognito subject identifies exactly one record (`userId` primary key).
The model authorizes against that same field using the JWT `sub` claim. This
prevents another user from creating, reading, or updating a goal at that key;
there is no separate owner value to mismatch with the key. AppSync enforces this
rule; the frontend is not the authorization boundary.

The dashboard loads only the current user's goal, resets when the authenticated
user changes, and saves through the user-pool authenticated data client. The
editor saves a weight alone. DailyTarget, FoodEntry and Vital are unchanged. No
existing goal is inferred from the old hardcoded value or from DailyTarget.
Accounts without a record show an unset goal, no remaining-weight estimate, and
no goal line. Cloud errors show a retry state and do not masquerade as unset.

The editor and feedback support English and Spanish. The native dialog traps
focus and supports Escape; saving disables repeat submits and closing. All three
dashboard consumers use the confirmed cloud response. Chart bounds include both
measured weights and goals, including goals above the current weight.

## Automated validation

Run `node --import tsx --test scripts/weight-goal*.test.ts` for data-flow tests with synthetic
accounts, invalid input, failed requests, cross-identity responses and chart
bounds. These tests do not substitute for deployed AppSync authorization tests.

The existing frontend build requires `amplify_outputs.json`, generated by
Amplify. Do not commit a dummy output file. Deploy the schema and regenerate
outputs before testing the real frontend. The new table is additive; existing
measurement tables and MCP IAM permissions are untouched.

## Deployed checks before marking Done

1. Sign in as account A, confirm the initial goal is unset, and set any test goal.
2. Refresh, sign out/in, and open another device/browser with account A. The
   same goal must appear in the card, remaining kilos and chart.
3. Sign in as B, confirm no goal from A is displayed, and save a different goal.
   Return to A and verify its value is unchanged.
4. With B's token, directly attempt get, create and update against A's userId.
   AppSync must deny access, and A's record must remain unchanged. Also attempt
   creation at A's key before A has created a goal: it must be denied.
5. Test save failures, retry after load failures, unset, decimal input, Spanish
   and English, keyboard interaction and a narrow mobile screen.
6. Confirm existing nutrition targets and weight/BP measurements are unchanged.

This change does not add MCP weight-goal tools. The existing DailyTarget tools
continue to operate on daily nutrition targets; exposing a goal-only connector
tool requires a separate authorized contract and tests.
